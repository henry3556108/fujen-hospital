# A-01 平台環境與底層庫建置：驗收操作劇本

> 本模組全部在**甲方測試環境**（真實 GPU 主機）執行。乙方開發機沒有真實 GPU，以下凡標「開發環境範例」者為 2026-10-03 在開發機（kind 叢集 `ai-platform`、假 GPU）實際執行的輸出，只用來讓操作人員知道畫面長什麼樣子，數字以甲方環境為準。
>
> **標示說明**
> - 〔待安裝腳本〕：依賴尚未完成的甲方主機安裝腳本（作業系統設定、Kubernetes、NVIDIA 驅動、GPU 調度元件）。腳本完成後，指令中的元件名稱（例如 `gpu-operator` 命名空間）可能需要依腳本調整，屆時更新本劇本。
> - GPU 版訓練映像 `platform-trainer-gpu`（2026-10-11 完成）：NVIDIA NGC TensorFlow 25.02 為基底（TensorFlow 2.17、CUDA 12.8、cuDNN 9），加上 PyTorch 2.8.0（cu128）。官方 TensorFlow 不支援這一代 GPU（RTX PRO 6000 Blackwell），所以 GPU 映像的 TensorFlow 版本比 CPU 映像（`platform-trainer`，`tensorflow-cpu==2.21.0`）舊。建置：`docker build -f platform/training/Dockerfile.gpu -t platform-trainer-gpu:<版本> platform/`。

## 共同前置條件

1. 甲方已提供測試環境主機（GPU 伺服器、CPU 伺服器）與管理權限，並已依安裝腳本完成：作業系統、Kubernetes、NVIDIA 驅動、GPU 調度元件（NVIDIA device plugin 或 GPU Operator）、Kueue、平台部署（`docs/delivery/部署說明.md` 第二部分「甲方正式環境」）。〔待安裝腳本〕
2. 操作電腦（或其中一台控制節點）可執行 `kubectl`，且 `kubectl config current-context` 指向甲方叢集。
3. 甲方提供「納管主機清單」（主機名稱、IP、角色：GPU／CPU、GPU 數量與型號），作為 TC-A01-02 的比對來源。M0 環境訪視紀錄中的 GPU 數量與型號也一併帶到現場。
4. 準備一個存證資料夾，例如 `中期測試紀錄/A-01/`，每一步的終端機輸出以 `指令 | tee <檔名>.txt` 存檔，並截圖。

## TC-A01-01 節點狀態

**合約指標**：作業系統「Linux 1 套（Ubuntu 或 Rocky Linux，版本依甲方指定）」，**安裝後節點 Ready 100%，異常 0 個**。

**前置條件**：共同前置條件 1、2。

**使用資料或帳號**：叢集管理者 kubeconfig；各主機 SSH 帳號（查作業系統版本用）。

**操作步驟**

1. 執行 `kubectl get nodes -o wide | tee A01-01-nodes.txt`
2. 執行
   ```bash
   kubectl get nodes -o custom-columns='節點:.metadata.name,就緒:.status.conditions[?(@.type=="Ready")].status,作業系統:.status.nodeInfo.osImage,核心:.status.nodeInfo.kernelVersion,容器執行環境:.status.nodeInfo.containerRuntimeVersion,K8s:.status.nodeInfo.kubeletVersion' | tee A01-01-nodeinfo.txt
   ```
3. 執行（列出不是 Ready 的節點，應無輸出）
   ```bash
   kubectl get nodes --no-headers | awk '$2 != "Ready"' | tee A01-01-notready.txt
   ```
4. 執行（列出任何節點的異常狀況：記憶體／磁碟／PID 壓力、網路未就緒，應無輸出）
   ```bash
   kubectl get nodes -o json | python3 -c 'import sys,json
   for n in json.load(sys.stdin)["items"]:
       for c in n["status"]["conditions"]:
           if c["type"]!="Ready" and c["status"]!="False": print(n["metadata"]["name"], c["type"], c["status"], c.get("message",""))' | tee A01-01-conditions.txt
   ```
5. 執行 `kubectl get pods -A --field-selector=status.phase!=Running,status.phase!=Succeeded | tee A01-01-pods.txt`（系統元件與平台元件沒有異常 Pod）。
6. 在每台主機執行 `cat /etc/os-release | head -3` 與 `uname -r`，或直接看步驟 2 的「作業系統」欄。

**預期結果**

- 步驟 1、2：每個節點「STATUS／就緒」都是 `Ready`／`True`；「作業系統」欄是甲方指定的同一套 Linux（例如 `Ubuntu 24.04.x LTS` 或 `Rocky Linux 9.x`），所有節點一致。
- 步驟 3、4、5：沒有任何輸出（只有標題列或 `No resources found`）。
- Ready 比例 = Ready 節點數 ÷ 節點總數 = 100%；異常 0 個。

開發環境範例（kind，作業系統為 kind 節點映像的 Debian，不代表甲方環境）：

```text
節點                        就緒   作業系統                       核心             容器執行環境         K8s
ai-platform-control-plane   True   Debian GNU/Linux 13 (trixie)   6.17.9-1-pve     containerd://2.3.4   v1.37.0
ai-platform-worker          True   Debian GNU/Linux 13 (trixie)   6.17.9-1-pve     containerd://2.3.4   v1.37.0
ai-platform-worker2         True   Debian GNU/Linux 13 (trixie)   6.17.9-1-pve     containerd://2.3.4   v1.37.0
ai-platform-worker3         True   Debian GNU/Linux 13 (trixie)   6.17.9-1-pve     containerd://2.3.4   v1.37.0
ai-platform-worker4         True   Debian GNU/Linux 13 (trixie)   6.17.9-1-pve     containerd://2.3.4   v1.37.0
```

**留存證據**：`A01-01-*.txt` 五個檔；步驟 1、2 的終端機截圖；每台主機的 `/etc/os-release` 輸出。紀錄「節點 N 個、Ready N 個、異常 0」。

**若結果不符**

- 節點 `NotReady`：在該主機查 `systemctl status kubelet`、`journalctl -u kubelet -n 50`；常見原因是 CNI 尚未就緒、kubelet 憑證或時間不同步（`timedatectl`）。
- 有 `MemoryPressure`／`DiskPressure`：查主機磁碟（`df -h /var/lib`）與記憶體；映像過多時清理 `crictl rmi --prune`。
- 系統 Pod 非 Running：`kubectl -n <命名空間> describe pod <名稱>` 看 Events。

**開發環境與甲方環境的差異**：開發機是 5 個 kind 節點（容器），作業系統顯示 Debian；甲方為實體／虛擬主機，節點名稱、數量與作業系統版本依甲方。

## TC-A01-02 納管差異

**合約指標**：「容器管理平台與 GPU 資源調度：容器編排平台 1 套、GPU 調度元件 1 套」，**納管節點清單與實際差異 0**；「硬體資源自動化納管：同時管理實體 GPU 伺服器與實體或虛擬 CPU 伺服器」，**節點差異 0 個**。

**前置條件**：共同前置條件 1–3；平台已部署，admin01 可登入。

**使用資料或帳號**：甲方的納管主機清單；平台帳號 `admin01`。

**操作步驟**

1. 執行 `kubectl version | tee A01-02-k8s-version.txt`（容器編排平台 1 套：Kubernetes）。
2. 執行 `kubectl -n kueue-system get deploy -o wide | tee A01-02-kueue.txt`（排程元件 Kueue）。
3. 執行 GPU 調度元件檢查〔待安裝腳本，命名空間依腳本而定〕：
   ```bash
   kubectl get pods -A -o wide | grep -Ei 'nvidia|gpu-operator|device-plugin|dcgm' | tee A01-02-gpu-components.txt
   ```
4. 執行（列出每個節點的池與 GPU 數）
   ```bash
   kubectl get nodes -o custom-columns='節點:.metadata.name,IP:.status.addresses[?(@.type=="InternalIP")].address,池:.metadata.labels.platform/pool,GPU:.status.capacity.nvidia\.com/gpu' | tee A01-02-nodes.txt
   ```
5. 以 `admin01` 登入平台網頁，點左側「帳號管理」→ 上方分頁「共享排程設定」→ 分頁「叢集節點」。截圖。
6. 逐列比對三份清單：甲方納管主機清單、步驟 4 的 kubectl 輸出、步驟 5 的平台「叢集節點」頁。比對欄位：主機名稱（節點）、角色（GPU／CPU，對應「節點池」）、GPU 數量（對應「實體 GPU」）。

**預期結果**

- 步驟 1：顯示 `Server Version`（例如 `v1.3x`）。步驟 2：`kueue-controller-manager` READY `1/1`。
- 步驟 3：GPU 調度元件（device plugin 或 GPU Operator 的 Pod）在每台 GPU 主機上各有 1 個且為 `Running`。
- 步驟 4、5：三份清單節點數相同、名稱一一對應；GPU 伺服器的「節點池」為 `gpu-exclusive` 或 `gpu-shared`，CPU 伺服器為 `cpu-web` 或 `cpu-data`；平台頁「實體 GPU」等於甲方清單的 GPU 數。差異 0 個。
- 平台頁上方 4 個數字：節點數、就緒節點相同；「實體 GPU」等於甲方清單 GPU 總數。

開發環境範例：平台「叢集節點」頁（`shots/TC-C01-01/01-叢集節點.png`）顯示節點數 5、就緒節點 5、實體 GPU 3、可排程 GPU 份數 6，與 `kubectl get nodes` 的 5 個節點一致。

**留存證據**：`A01-02-*.txt`；平台「叢集節點」頁截圖；三份清單的比對表（可用 Excel，一列一台主機，最後一欄「一致／不一致」）。

**若結果不符**

- 平台頁少了節點：該主機未加入叢集（`kubeadm join` 未完成）或平台 API 沒有讀 Node 的權限（`kubectl auth can-i list nodes --as=system:serviceaccount:ai-platform:platform-api`）。
- 節點池欄顯示「—」：該節點沒有 `platform/pool` 標籤，依安裝腳本補 `kubectl label node <節點> platform/pool=<池>`。
- 實體 GPU 為 0：沒有 `platform/gpu-physical` 標籤或 device plugin 沒有在該節點執行。

**開發環境與甲方環境的差異**：開發機 GPU 是以 node status 宣告的假 GPU（worker3 2 張、worker4 1 張切 4 份），沒有 device plugin，步驟 3 在開發機沒有輸出。

## TC-A01-03 GPU 驅動與底層庫

**合約指標**：「GPU 驅動與 AI 底層庫：CUDA、cuDNN、PyTorch、TensorFlow」，**GPU 檢測 3 次，全部偵測，驅動衝突 0 項**。

**前置條件**：共同前置條件 1、2；NVIDIA 驅動已安裝（R570 以上，CUDA 12.8 需要）〔待安裝腳本〕；GPU 版訓練映像 `platform-trainer-gpu` 已推到甲方 registry 或載入每台 GPU 主機。

**使用資料或帳號**：GPU 主機 SSH 帳號；叢集管理者 kubeconfig；檢查用 Job 檔 `docs/acceptance-kit/m1/files/TC-A01-03-gpu-check.yaml`。

**操作步驟**（第 1–4 步在每台 GPU 主機上做；第 5–8 步在操作電腦做；整組重複 3 次，第 2、3 次把檔名的 `-1` 改 `-2`、`-3`）

1. 在 GPU 主機執行 `nvidia-smi | tee A01-03-nvidia-smi-<主機>-1.txt`
2. 執行 `nvidia-smi --query-gpu=index,name,driver_version,memory.total --format=csv | tee -a A01-03-nvidia-smi-<主機>-1.txt`
3. 執行（驅動衝突檢查，應無輸出）：
   ```bash
   lsmod | grep -i nouveau; dmesg 2>/dev/null | grep -iE 'NVRM.*(mismatch|failed)|version mismatch' | tail -5
   ```
4. 執行 `nvcc --version 2>/dev/null || echo "主機未裝 CUDA toolkit（以容器內 CUDA 為準）"`
5. 在操作電腦執行（把 `<GPU 版訓練映像>` 換成實際映像位址，例如 `<registry>/platform-trainer-gpu:<版本>`）：
   ```bash
   sed "s#IMAGE#<GPU 版訓練映像>#; s#RUN#1#" docs/acceptance-kit/m1/files/TC-A01-03-gpu-check.yaml | kubectl apply -f -
   ```
6. 執行 `kubectl -n platform-jobs wait --for=condition=complete job/tc-a01-03-gpu-check-1 --timeout=300s`
7. 執行 `kubectl -n platform-jobs logs job/tc-a01-03-gpu-check-1 | tee A01-03-container-1.txt`
8. 若有 `gpu-shared` 主機，把檔案裡的 `gpu-exclusive`（兩處）改成 `gpu-shared` 再做一次步驟 5–7。
9. 三次都做完後執行 `kubectl -n platform-jobs delete job -l acceptance=tc-a01-03`。

**預期結果**

- 步驟 1、2：列出的 GPU 數量與型號等於 M0 訪視紀錄（例如 `0, NVIDIA H100 80GB HBM3, 5xx.xx, 81559 MiB`），每張 GPU 都出現；最上方的 `Driver Version` 與 `CUDA Version` 有值。三次結果相同。
- 步驟 3：沒有輸出（沒有 nouveau 模組、沒有驅動版本不符訊息）＝驅動衝突 0 項。
- 步驟 7 的輸出（每次）應有下列 5 行，且 GPU 數 ≥ 1、兩個「GPU 運算」為 `True`：
  ```text
  節點: <GPU 節點>  Python: 3.12.x
  nvidia-smi: 0, NVIDIA <型號>, <驅動版本>, <顯存> MiB
  PyTorch: 2.8.0+cu128  CUDA: 12.8  cuDNN: 91002  GPU 數: 1  可用: True
  PyTorch GPU 運算: True
  TensorFlow: 2.17.0  CUDA: 12.8  cuDNN: 9  GPU 數: 1
  TensorFlow GPU 運算: True
  ```
- 把 PyTorch 與 TensorFlow 回報的 CUDA、cuDNN 版本記入版本清單（TC-A01-04 一併交付）。

開發環境範例（2026-10-11，開發機 Windows 驅動 572.83 + WSL2，以 `docker run --gpus all platform-trainer-gpu:dev python /src/training/scripts/gpu_check.py` 執行同一段檢查程式；開發機的 kind 叢集是假 GPU，所以不是經 Kubernetes Job）：

```text
節點: ?  Python: 3.12.3
nvidia-smi: 0, NVIDIA RTX PRO 6000 Blackwell Workstation Edition, 572.83, 97887 MiB
PyTorch: 2.8.0+cu128  CUDA: 12.8  cuDNN: 91002  GPU 數: 1  可用: True
PyTorch GPU 運算: True
TensorFlow: 2.17.0  CUDA: 12.8  cuDNN: 9  GPU 數: 1
TensorFlow GPU 運算: True
```

同一個映像的影像範本在 GPU 上訓練、重跑 3 次權重逐位元相同（`platform/training/scripts/test-gpu-image.sh`）。舊的 CPU 映像 `platform-trainer:dev` 執行同一段檢查只會得到 `No module named 'torch'` 與 `GPU 數: 0`，**Job 檔的 IMAGE 一定要用 GPU 映像**。

**留存證據**：每台 GPU 主機 3 次的 `A01-03-nvidia-smi-*.txt`；3 次的 `A01-03-container-*.txt`；`nvidia-smi` 畫面截圖 3 張；在中期測試紀錄填「GPU 檢測 3 次：偵測 X/X 張，驅動衝突 0」。

**若結果不符**

- `nvidia-smi` 顯示 `NVIDIA-SMI has failed` 或 `Driver/library version mismatch`：驅動與核心模組版本不一致，通常是更新驅動後未重開機；重開機或依安裝腳本重裝驅動。
- 有 nouveau：未停用開源驅動，依安裝腳本加入 `blacklist nouveau` 後重建 initramfs 並重開機。
- Job 一直 `Pending`：`kubectl -n platform-jobs describe pod -l acceptance=tc-a01-03` 看 Events；常見為節點沒有 `nvidia.com/gpu` 資源（device plugin 未啟動）或 Kueue 配額已滿（先等其他工作結束）。
- 容器內 `GPU 數: 0`：容器沒有使用 NVIDIA runtime（containerd 未設定 nvidia runtime 或 RuntimeClass），或映像是 CPU 版（`platform-trainer`）。
- `No module named 'torch'`：用錯映像，IMAGE 要換成 `platform-trainer-gpu`。
- TensorFlow `GPU 數: 0` 但 PyTorch 正常：驅動版本低於 CUDA 12.8 的需求，`nvidia-smi` 右上角的 `CUDA Version` 要 ≥ 12.8。

**開發環境與甲方環境的差異**：開發機有同型號的 GPU（1 張），但 kind 叢集內的 GPU 是假的，所以開發範例以 `docker run --gpus all` 執行同一段檢查；經 Kubernetes Job 的步驟 5–7 只能在甲方執行。

## TC-A01-04 Python 套件

**合約指標**：「Python 開源套件部署：依雙方確認清單安裝常用演算法套件」，**清單與實裝差異 0 項，產出版本清單**。

**前置條件**：甲方已回覆確認套件清單（《M1 應備事項需求函》第 109 行附近）；乙方已把確認後的清單放在 `docs/delivery/python-packages/`（每個映像一個 `.txt`，一行一個 `套件==版本`）；平台已部署。

**使用資料或帳號**：乙方工作機（有 Docker 與 `uv`，可存取甲方 registry）；叢集管理者 kubeconfig。

**操作步驟**

1. 在乙方工作機進入 `platform/compliance`，執行 `uv sync`。
2. 執行 `uv run python -m compliance packages check | tee A01-04-check.txt`（第一次約 20 分鐘，會建置平台映像並以 Syft 掃描所有映像；建議前一天先跑一次，現場以 `--reuse` 沿用掃描結果：`uv run python -m compliance packages check --reuse`）。
3. 現場抽驗「實裝」：直接在執行中的容器列出套件，與清單比對（以訓練／推論映像為例）：
   ```bash
   kubectl -n ai-platform exec deploy/inference -- python -c "import importlib.metadata as m;print('\n'.join(sorted({f'{d.metadata[\"Name\"].lower().replace(\"_\",\"-\")}=={d.version}' for d in m.distributions()})))" > A01-04-inference-actual.txt
   diff <(sort -f docs/delivery/python-packages/image-docker.io_library_platform-trainer_dev.txt) <(sort -f A01-04-inference-actual.txt) | tee A01-04-diff.txt
   ```
   （甲方環境的清單檔名依映像位址而定，例如 `image-<registry>_platform-trainer_<版本>.txt`。）
4. 產出交付用版本清單：`uv run python -m compliance packages generate --reuse`，把 `docs/delivery/python-packages/` 整個資料夾附入「平台環境與底層庫版本清單」。

**預期結果**

- 步驟 2 最後一行：`PASS  TC-A01-04     映像內 Python 套件與已確認清單差異 0（映像 N、套件 M）`。
- 步驟 3：`A01-04-diff.txt` 只能出現打包工具隨附的套件（`pip`、`setuptools`、`wheel` 以及它們內附的 `jaraco-*`、`more-itertools`、`zipp`、`tomli`、`autocommand`、`backports-tarfile`、`importlib-metadata`、`platformdirs`、`packaging==26.0`，以及建置工具 `hatchling`、`pathspec`、`pluggy`、`tomlkit`、`trove-classifiers`，Syft 從映像檔案掃得到，但 Python 執行時不列出）；演算法套件（numpy、pandas、scipy、scikit-learn、statsmodels、lifelines、tensorflow、torch 等）不得出現在差異中。
- 步驟 4：`docs/delivery/python-packages/` 每個映像一個清單檔。

開發環境範例（2026-10-03）：

- 目前已確認清單有 7 個檔（`build-api.txt`、`build-fakes.txt`、`build-training.txt`、`image-docker.io_library_platform-trainer_dev.txt`、`image-docker.io_library_python_3.12-alpine.txt`、`image-docker.io_library_python_3.12-slim-trixie.txt`、`image-ghcr.io_mlflow_mlflow_v3.16.1.txt`）。訓練映像清單 97 行，包含 `numpy==2.5.3`、`pandas==3.0.6`、`scipy==1.18.1`、`scikit-learn==1.9.1`、`statsmodels==0.15.0`、`lifelines==0.30.0`、`tensorflow-cpu==2.21.0`；**沒有 torch**。
