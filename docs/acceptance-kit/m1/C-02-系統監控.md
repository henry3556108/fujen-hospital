## TC-C02-01 監控目標

**合約指標**：「監控目標設定：服務發現或靜態配置」，**抓取指標與設定差異 0**；測試案例：比對 Prometheus 目標與已部署服務清單，差異 0（監控覆蓋檢查）。

> **目前不通過（見文末缺陷 1）**：平台本身（命名空間 `ai-platform` 的 18 個服務）沒有列入監控目標或覆蓋政策，覆蓋檢查 FAIL。下方「預期結果」是修正後應有的樣子；未修正前現場不要執行步驟 4 給甲方看。

**前置條件**：共同前置條件 1、3。

**使用資料或帳號**：無需平台帳號。

**操作步驟**

1. 瀏覽器開 Prometheus，點上方「Status」→「Target health」（網址 `/targets`）。截圖。
2. 執行（目前的抓取目標與狀態）：
   ```bash
   curl -s 'http://127.0.0.1:39090/api/v1/targets?state=active' | python3 -c 'import sys,json;from collections import Counter
   c=Counter((t["labels"]["job"],t["health"]) for t in json.load(sys.stdin)["data"]["activeTargets"])
   [print(j,h,n) for (j,h),n in sorted(c.items())]' | tee C02-01-targets.txt
   ```
3. 執行（已部署服務清單）：`kubectl get deploy,statefulset,daemonset -A | tee C02-01-workloads.txt`
4. 在 `platform/compliance` 執行覆蓋檢查（自動比對 2 與 3）：
   ```bash
   uv run python -m compliance monitoring | tee C02-01-coverage.txt
   ```
   （甲方環境加 `--kube-context <context> --prometheus <網址>`，見 `uv run python -m compliance monitoring --help`。）

**預期結果**（`shots/TC-C02-01/01-Prometheus目標.png`）

- 步驟 1：每個抓取工作都是綠色「UP」，例如 `alertmanager 1 / 1 up`、`cadvisor 5 / 5 up`。
- 步驟 2（開發環境實測）：`alertmanager up 1`、`cadvisor up 5`、`grafana up 1`、`kube-state-metrics up 1`、`kubelet up 5`、`kueue-controller-manager up 1`、`prometheus up 1`。kubelet、cadvisor 各等於節點數 5。沒有 `down`。
- 步驟 4 最後一行應為 `PASS  TC-DAILY-02  叢集服務 N：抓取目標 …、容器指標 …、未覆蓋 0；目標異常 0；節點缺口 0`。
- **開發環境 2026-10-03 實測**：`FAIL  TC-DAILY-02   叢集服務 25：抓取目標 5、容器指標 2、未覆蓋 18；目標異常 0；節點缺口 0`，未覆蓋的 18 個全是 `ai-platform/*`（api、apisix、keycloak、postgres、minio、web…）。這 18 個 Pod 在 Prometheus 都有 cAdvisor 容器指標（`count by (pod)(container_memory_working_set_bytes{namespace="ai-platform",container!=""})` 回 18 筆），只是政策檔沒有列入。

**留存證據**：Target health 截圖；`C02-01-*.txt`（含 PASS 行）。

**若結果不符**

- 某目標 `DOWN`：在 Target health 看「Error」欄；常見為服務 Pod 重啟中或 NetworkPolicy 擋住 Prometheus。

- `節點缺口`：新節點的 kubelet／cAdvisor 尚未被抓到，等 1 分鐘或查節點 10250 埠。

**開發環境與甲方環境的差異**：開發環境另有 `platform-web/web-echo`、`monitoring/mailpit` 測試服務；甲方多 DCGM exporter（每台 GPU 主機 1 個目標），節點數依甲方。

## TC-C02-02 5 類指標

**合約指標**：「即時資源監控：節點、Pod、CPU、記憶體、GPU 五類指標」，**抽查 3 次，與監控來源差異 0**。

**前置條件**：共同前置條件 1、3。

**使用資料或帳號**：無。

**操作步驟**（整組做 3 次，每次間隔至少 10 秒；每次的 Prometheus 畫面與 kubectl 輸出都存檔）

1. Prometheus 點「Query」，在輸入框貼上下列查詢，點「Execute」，切到「Table」：`count(kube_node_info)`。截圖。
2. 執行 `kubectl get nodes --no-headers | wc -l`。
3. 查詢 `count(kube_pod_info{namespace="ai-platform"})`，截圖；執行 `kubectl -n ai-platform get pods --no-headers | wc -l`。
4. 查詢（CPU 與記憶體：平台 API 容器的 CPU 請求量與記憶體上限）：
   `kube_pod_container_resource_requests{namespace="ai-platform",pod=~"api-.*",resource="cpu"} or kube_pod_container_resource_limits{namespace="ai-platform",pod=~"api-.*",resource="memory"}`，截圖；
   執行 `kubectl -n ai-platform get pod -l app=api -o jsonpath='{.items[0].spec.containers[0].resources}{"\n"}'`。
5. 查詢（節點 CPU 核數與記憶體）：`kube_node_status_capacity{resource=~"cpu|memory"}`；
   執行 `kubectl get nodes -o custom-columns='節點:.metadata.name,CPU:.status.capacity.cpu,記憶體:.status.capacity.memory'`。
6. 查詢（實際使用量，確認有即時值）：`sum by (pod) (rate(container_cpu_usage_seconds_total{namespace="ai-platform",container!=""}[1m]))`，切到「Graph」看曲線。
7. 查詢（GPU）：`kube_node_status_capacity{resource="nvidia_com_gpu"}`，截圖；執行 `kubectl get nodes -o custom-columns='節點:.metadata.name,GPU:.status.capacity.nvidia\.com/gpu'`。
8. 甲方環境另做（GPU 使用率，需 DCGM）：查詢 `DCGM_FI_DEV_GPU_UTIL`、`DCGM_FI_DEV_FB_USED`、`DCGM_FI_DEV_GPU_TEMP`；同時在 GPU 主機執行 `nvidia-smi --query-gpu=index,utilization.gpu,memory.used,temperature.gpu --format=csv`。〔待安裝腳本：DCGM exporter〕
9. （選做）Grafana 開「Dashboards」→ 資料夾「平台」→「平台叢集總覽」，截圖（`shots/TC-C02-02/05-Grafana平台叢集總覽.png`）。

**預期結果**（`shots/TC-C02-02/01-節點數.png`～`04-GPU份數.png`）

| 類別 | Prometheus（開發環境實測） | 來源（kubectl） | 差異 |
|---|---|---|---|
| 節點 | `count(kube_node_info)` = `5` | 5 | 0 |
| Pod | `count(kube_pod_info{namespace="ai-platform"})` = `24` | 24 | 0 |
| CPU | api 容器 cpu requests = `0.1` | `"requests":{"cpu":"100m",…}` = 0.1 核 | 0 |
| 記憶體 | api 容器 memory limits = `1610612736` | `"limits":{…,"memory":"1536Mi"}` = 1536×1024² | 0 |
| 節點 CPU／記憶體 | 每節點 cpu `56`、memory `33519693824` | `56`、`32734076Ki`（×1024 相同） | 0 |
| GPU（份數） | worker3 `2`、worker4 `4` | worker3 `2`、worker4 `4`，其他 `<none>`（Prometheus 不列） | 0 |
| GPU（使用率等） | 甲方：`DCGM_FI_DEV_GPU_UTIL` 等 | 甲方：`nvidia-smi` | 甲方驗；使用率會跳動，比對同一時間點、容許取樣差 |

- 步驟 6：每個 ai-platform Pod 都有曲線（有即時值）。
- Pod 數會隨工作變動，抽查時兩邊要在 10 秒內查完；若剛好有 Pod 建立或結束而不同，重查一次並在紀錄註明。

**留存證據**：3 次 × 5 類的截圖與 kubectl 輸出（建議存成 `C02-02-第1次.txt` 等）；比對表。

**若結果不符**：Prometheus 沒有值：查 TC-C02-01 的 `kube-state-metrics` 目標是否 UP；數字差 1：多半是查詢之間有 Pod 建立／刪除，重查。

**開發環境與甲方環境的差異**：開發環境 GPU 為假 GPU，只有「份數」，沒有使用率、顯存、溫度；甲方以 DCGM 指標與 `nvidia-smi` 比對。開發環境 kind 節點都顯示宿主機的 56 核與 32 GB。

## TC-C02-04 告警（含破壞性步驟，需協調）

**合約指標**：「異常告警：3 類事件、3 條發送規則、重複告警抑制」，**送出成功 100%，抑制後重複 0**。

告警規則（Prometheus「Alerts」頁可見 3 條，`shots/TC-C02-04/00-Prometheus告警規則.png`）：

| 規則 | 事件類別 | 條件 | 等級 |
|---|---|---|---|
| `PlatformJobFailed` | 平台工作失敗 | `platform-jobs` 內有 Job 失敗 | warning |
| `HighPodCpu` | 資源異常 | 單一 Pod CPU 超過 0.8 核持續 20 秒 | warning |
| `NodeNotReady` | 節點失聯 | 節點 Ready≠true 持續 10 秒 | critical |

發送：Alertmanager 以 email 寄到 `ops@ai-platform.local`（開發環境由 Mailpit 收；甲方改為甲方告警管道）。抑制：同一告警群組只寄一次，4 小時內不重寄、不寄「已解除」；節點未就緒時抑制同節點上的 warning。

> **說明「3 條發送規則」**：目前是 3 條告警規則共用 1 條發送路由（全部寄給維運信箱）。若甲方要求「3 條發送路由」（例如依等級寄不同收件人），需在 `platform/deploy/kind/monitoring/alertmanager.yaml` 的 `route.routes` 補上，現場前須與甲方確認解讀。

**前置條件**

- 事件 2、3 會影響整個叢集（節點 `ai-platform-worker4` 暫停約 3 分鐘，共享池工作無法執行；`cpu-data` 節點一顆核忙碌約 6 分鐘），**只能在沒有其他人使用叢集時執行**。
- 上一輪的節點告警已結束：Alertmanager 首頁沒有 `NodeNotReady`（`keep_firing_for` 1 分鐘，`HighPodCpu` 5 分鐘）。
- 檔案 `docs/acceptance-kit/m1/files/TC-C02-04-cpu-burner.yaml`。

**使用資料或帳號**：`admin01`（送失敗工作）；可執行 docker 與 kubectl 的開發機帳號。

**操作步驟**

1. 清空告警收件匣：Mailpit 點「Delete all」並確認（或 `curl -s -X DELETE http://127.0.0.1:38025/api/v1/messages`）。
2. 事件 1（工作失敗）：平台「目前專案」`KIT-C-p1` →「建模管理」→「專案工作」；「執行秒數」`5`，勾選「讓這件工作以失敗結束（測試佇列不會卡住）」，點「送出工作」。記下 Kubernetes Job 名稱：`kubectl -n platform-jobs get jobs --sort-by=.metadata.creationTimestamp | tail -1`。
3. 事件 2（CPU 過高）：`kubectl apply -f docs/acceptance-kit/m1/files/TC-C02-04-cpu-burner.yaml`
4. 事件 3（節點失聯）：開發環境 `docker pause ai-platform-worker4`；甲方環境在一台**不影響驗收進行**的測試節點執行 `sudo systemctl stop kubelet`。
5. 等 2 分鐘。開 Alertmanager 首頁，截圖（3 個告警群組都在）。
6. 開 Mailpit，截圖（3 封信）。
7. 再等 2 分鐘（超過 `group_interval` 1 分鐘＋評估週期），重新整理 Mailpit，截圖，並執行：
   ```bash
   curl -s 'http://127.0.0.1:38025/api/v1/messages?limit=50' | python3 -c 'import sys,json;[print(m["Subject"]) for m in json.load(sys.stdin)["messages"]]' | tee C02-04-mails.txt
   ```
8. 恢復：`docker unpause ai-platform-worker4`（甲方 `sudo systemctl start kubelet`）；`kubectl -n platform-web delete pod kit-cpu-burner --grace-period=0`；`kubectl wait --for=condition=Ready node --all --timeout=180s`；`kubectl get nodes`。
9. 刪除失敗的測試 Job（否則 `PlatformJobFailed` 持續觸發，每 4 小時重寄）：`kubectl -n platform-jobs delete job <步驟 2 的 Job 名稱>`。

**預期結果**（2026-10-03 19:05 實際執行：`shots/TC-C02-04/00-清空收件匣.png`、`02-Alertmanager三類告警.png`、`03-Mailpit收到3封.png`、`04-等候2分鐘後仍3封.png`）

- 步驟 5：Alertmanager 有 `alertname="PlatformJobFailed" job_name="job-…"`、`alertname="HighPodCpu" pod="kit-cpu-burner"`、`alertname="NodeNotReady" node="ai-platform-worker4"`。
- 步驟 6、7：Mailpit 恰好 3 封，寄件者 `alertmanager@ai-platform.local`、收件者 `ops@ai-platform.local`，主旨：
  - `[FIRING:1] PlatformJobFailed job-<編號>-<代碼> platform-jobs (… BackoffLimitExceeded warning)`（開發環境實例：`[FIRING:1] PlatformJobFailed job-86-55d7bc platform-jobs (kube-state-metrics.monitoring.svc:8080 kube-state-metrics BackoffLimitExceeded warning)`）
  - `[FIRING:1] HighPodCpu platform-web ai-platform-worker2 kit-cpu-burner (warning)`
  - `[FIRING:1] NodeNotReady ai-platform-worker4 (Ready kube-state-metrics.monitoring.svc:8080 kube-state-metrics critical true)`
- 開發環境實測到信時間：工作失敗 19:05:30（送出後約 20 秒）、節點失聯 19:06:00（暫停後約 50 秒）、CPU 過高 19:06:40（約 90 秒）。所以步驟 5 至少等 2 分鐘。
- 步驟 7 等候後仍是 3 封（19:08:46 再查，`total 3`，3 個告警仍在觸發中）：送出成功 3/3＝100%，重複 0。
- Alertmanager 首頁會同時看到之前留下的 `PlatformJobFailed` 群組（舊的失敗 Job），屬缺陷 2；現場前先依步驟 9 清除舊失敗 Job。

**留存證據**：Alertmanager、Mailpit（步驟 6、7）截圖；`C02-04-mails.txt`；恢復後 `kubectl get nodes` 輸出。

**若結果不符**

- 少了 NodeNotReady：上一輪同節點告警仍在 `keep_firing_for` 期間，被視為同一件事不重寄；等 Alertmanager 沒有該告警後重做。
- 少了 HighPodCpu：節點 CPU 不足使忙迴圈達不到 0.8 核（`kubectl top` 不可用時看 Prometheus `rate(container_cpu_usage_seconds_total{pod="kit-cpu-burner"}[1m])`）。
- 信件重複：查 `alertmanager.yaml` 的 `repeat_interval` 與 `group_by`；Alertmanager 重啟會清掉通知紀錄而重寄。
- 甲方收不到：SMTP 設定（`smtp_smarthost`）或甲方郵件閘道擋信，查 `kubectl -n monitoring logs deploy/alertmanager | grep -i notify`。

**開發環境與甲方環境的差異**：開發環境以 `docker pause` 模擬節點失聯、Mailpit 收信；甲方以停止測試節點 kubelet 模擬，收件為甲方指定告警管道（《應備事項需求函》10/12 前提供）。

## 本次演練發現的問題（2026-10-03）

1. **監控覆蓋不含平台本身**（嚴重，阻擋 TC-C02-01）：平台改部署到 Kubernetes（命名空間 `ai-platform`）後，`platform/compliance/policy/monitoring.yaml` 與 Prometheus 抓取設定沒有跟著更新。`uv run python -m compliance monitoring` 回 `FAIL … 未覆蓋 18`。自動測試 `test_tc_c02_01` 只檢查 `monitoring`、`kueue-system`、`platform-web` 三個命名空間，所以測試通過但實際部署不通過。修正方向：為有 `/metrics` 的服務（APISIX、Keycloak、MinIO、平台 API 等）加抓取工作，其餘列入 `container_metrics_only`，並把 `ai-platform` 加進測試的命名空間清單。
2. **失敗的工作每 4 小時重寄告警**（一般，影響「抑制後重複 0」的觀感）：失敗的 Kubernetes Job 不會被清除，`PlatformJobFailed` 一直處於觸發中，Alertmanager 依 `repeat_interval: 4h` 重寄。Mailpit 實例（UTC）：`job-30-59897a` 在 09:18、13:18、17:18，`job-31-971b07` 在 09:22、13:22、17:22，各收到 3 封。驗收前須清除舊失敗 Job，或改規則只看最近失敗（例如 `changes(kube_job_status_failed[10m]) > 0`）。
3. Mailpit 另有 09:01 的 `HighPodCpu` 告警（`monitoring/grafana-…`、`kube-system/etcd-…`），開發機忙碌時會出現，現場前先清空收件匣。
4. GPU 使用率、顯存、溫度指標需甲方安裝 DCGM exporter（已知缺口）。
