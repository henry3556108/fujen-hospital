## 專案資料清理（第 6 項）

採 outbox：**資料庫是唯一事實來源，外部清理一定晚於資料庫 commit，失敗可重試。**

1. `delete_project` 在同一個交易內：刪影像與結構式索引列（不依賴資料庫 CASCADE，SQLite 與 PostgreSQL 行為一致）、寫 `storage_cleanup_tasks`（待清理清單）、寫稽核、刪專案。
   - 物件儲存：1 筆 `object_prefix` = `projects/{pid}/`（影像檔、CSV、之後工作包放在同前綴下的檔案都涵蓋）。
   - Orthanc：每個「其他專案沒有引用」的 SOP Instance UID 1 筆。Orthanc 是跨專案共用的節點，兩個專案匯入同一張影像時只存一份，所以還有別的專案引用就不刪。
2. commit 之後才執行清理；成功的工作刪掉，失敗的留著（記次數與最後錯誤）。刪除 API 仍回 204：專案在平台上已經不存在，殘留的只是使用者看不到的孤兒資料。
3. 清理結果寫 1 筆 `dataset` 類稽核 `project.data_cleanup`（result=`success`／`partial`，detail 記成功與失敗數）。
4. 重試：之後任何一次專案刪除、種子重設都會順便重跑殘留工作；也可手動 `python -m app.project_cleanup`。
5. 種子重設走同一套清理。未設定影像節點（`ORTHANC_URL` 空）時 Orthanc 工作留在清單裡等之後重試。
6. 結構式資料的 DataFrame 快取依前綴清掉，避免專案編號被重用時讀到舊資料。

`OrthancClient` 介面新增 `delete(sop_instance_uid)`（找不到視為已刪除）。

## 不做的項目與理由

- **被拒絕的操作（403、409）寫稽核**：契約的 8 類稽核只要求成功的變更；這是政策決定，留給使用者與甲方。選項：
  (a) 維持現狀（目前 Gateway 與 API 存取日誌已有 403 紀錄，但不在稽核表）；
  (b) 只記「寫入類」被拒（POST／PUT／PATCH／DELETE 的 403、409）：量小，能回答「誰試過越權」，實作是一個全域 exception handler 加獨立交易，約半天；
  (c) 連讀取的 403 都記：量大、容易被刷爆（未授權者可以灌稽核表），需要配速率限制與保留期限。
  建議 (b)，但要先確認稽核表的保留期限與是否算進 TC-D01-05 的抽查母體。
- OHIF bulk data 路徑（Orthanc `PublicRoot`）：屬 WP5 標註。
- 正式環境設定（關閉 `directAccessGrantsEnabled`、CORS 網域、替換開發密碼）：開發機不適用。
- Orthanc 映像只有 amd64：無可修。
