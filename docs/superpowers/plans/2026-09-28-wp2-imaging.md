# WP2 醫療影像匯入（B-01）Implementation Plan

**Goal:** 影像能進平台（網頁／API、批次 CLI、PACS 查詢取像），依專案建立研究／序列索引，Accession 清單限制在網頁、API、DICOMweb 三個入口一致生效。

**Architecture:** 平台 Orthanc 是平台自己的 DICOM 節點（像素資料只存這裡），PostgreSQL 存專案範圍的索引、Accession 清單、匯入工作與逐檔結果、標註配對。NIfTI／ITK／makesense 檔案存物件儲存（本機 Local、整合環境 MinIO）。平台 API 透過 `OrthancClient` 介面操作 Orthanc；單元測試用記憶體版，不需 Docker。DICOMweb 只經 APISIX：`/dicomweb/projects/{pid}/...` → forward-auth `/authz/check`（專案權限＋研究在專案內＋Accession 在清單內）→ Orthanc `/dicom-web/...`。

**Spec:** 驗收案例 TC-B01-01～09、TC-SS-05。

## Endpoints（前綴 `/api/projects/{project_id}/imaging`）

| 方法 | 路徑 | 權限 | 說明 |
|---|---|---|---|
| POST | `/dicom` | labeling | 多檔上傳 DICOM；逐檔結果（imported／duplicate／failed＋原因）；建立 ImportJob |
| POST | `/files` | labeling | NIfTI（.nii/.nii.gz）、ITK（.mha）、makesense（.json）；解析驗證、存物件儲存、配對 |
| GET | `/files` | project | 非 DICOM 檔清單與配對狀態 |
| GET | `/jobs`、`/jobs/{job_id}` | project | 匯入工作與逐檔錯誤 |
| GET | `/studies?modality=&patient_sex=&study_description=&study_date=&series_description=` | project | 5 欄位篩選；套用 Accession 清單 |
| GET | `/studies/{study_uid}` | project | 研究明細；清單外或不在專案 → 404 |
| GET | `/accession-allowlist` | project | 目前清單 |
| PUT | `/accession-allowlist` | Admin | 設定清單（空清單＝不限制）；稽核 dataset |
| POST | `/pacs/query` | labeling | C-FIND（Study 層級）；受限專案只回清單內 |
| POST | `/pacs/retrieve` | labeling | C-MOVE 到平台節點後建立索引；清單外 403 |
| GET | `/dicomweb/projects/{pid}/studies/{uid}[/series/{uid}[/instances/{uid}]]/...`（經 Gateway） | project | forward-auth；僅 GET/HEAD |
| GET | `/dicomweb/projects/{pid}/studies?StudyInstanceUID={uid}` | project | 唯一允許的 QIDO 搜尋形式（避免列出其他專案的研究） |

## Data Flow

1. 上傳 DICOM → 解析驗證（失敗只記該檔）→ 專案內同 SOP Instance UID 已存在 → duplicate（不再送 Orthanc）→ 送 Orthanc → 寫索引 → ImportJob + 逐檔結果 + 一筆 dataset 稽核（同一交易）。
2. NIfTI／ITK：`<case>_image.*`、`<case>_label.*` 以 case＋格式配對；makesense：`images[].file_name` 對專案內 DICOM 的來源路徑（完全相同或以 `/file_name` 結尾，唯一才配）。每次匯入後重新配對尚未配對的標註，所以「先標註後影像」「分開匯入」都成立；只在同一專案內配對。
3. PACS：平台 Orthanc `/modalities/pacs/query` → answers；retrieve 用 `/modalities/pacs/move`（TargetAet=平台 AET），完成後從平台 Orthanc 取回該研究的檔案，走同一個索引流程（Orthanc 端已存在不重送）。
4. DICOMweb：APISIX forward-auth 把原始 `X-Forwarded-Uri`、`X-Forwarded-Method` 交給 `/authz/check`；非正規路徑、非 GET、不在專案索引、清單外、series／instance 不屬於該研究 → 403。通過後 proxy-rewrite 到 Orthanc 並由 Gateway 補 Orthanc Basic 認證。

## 需甲方確認的決定（先照此實作）

1. **匯入權限＝Labeling**（MD、RA、PI）；Viewer、Coder Assistant 不能匯入。查詢類只需 Project。
2. **Accession 清單只有 Admin 能設定**；空清單＝該專案不限制。清單是「存取過濾」而不是「匯入過濾」：清單外的研究可以匯入，但網頁、API、DICOMweb 都看不到；PACS 取像則直接拒絕清單外研究。
3. **去重範圍是專案**：同一 SOP Instance UID 在同專案第二次匯入記為 duplicate；Orthanc 端本來就只存一份。
4. **DICOMweb 唯讀**（不開 STOW）；研究列表搜尋只允許 `StudyInstanceUID=` 單一 UID 形式，OHIF 以指定研究方式開啟（WP5）。
5. CLI 以 Keycloak device-code 登入（本機可用 password grant），token 存在使用者目錄，未登入一律不上傳。

## 實作備註

- Orthanc 映像用 `jodogne/orthanc-plugins:1.13.0`（289 MB，含 DICOMweb；只有 amd64，在 Apple Silicon 以模擬執行）。`orthancteam/orthanc` 有 arm64 但約 680 MB。只載入 DICOMweb 外掛。
- MinIO 官方映像已不在 Docker Hub／quay 公開提供，改用 `cgr.dev/chainguard/minio:latest`（API 相同）。
- APISIX：`proxy-rewrite` 在 rewrite 階段、`forward-auth` 在 access 階段；Orthanc 的 Basic 認證改由 access 階段最後的 `serverless-post-function` 設定，否則 forward-auth 收到的是 Basic 而不是使用者的 Bearer。
- 刪除專案（含 seed 重建）時 PostgreSQL 以 ON DELETE CASCADE 清掉影像索引；Orthanc 內的影像與物件儲存的檔案不會自動刪除（待 WP8 資料保存政策決定）。
