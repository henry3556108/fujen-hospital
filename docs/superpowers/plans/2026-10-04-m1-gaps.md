## 1. 標註群組

**設計**
- 資料表 `label_groups`（id、project_id → projects ON DELETE CASCADE、name、description、created_by、created_at；`(project_id, name)` 唯一）
  與 `label_group_members`（group_id → label_groups CASCADE、user_id → users CASCADE；`(group_id, user_id)` 唯一）。
- 群組屬於一個專案；成員必須是該專案的成員（不是成員回 409，訊息列出帳號）。
- Admin API（`/api/admin/projects/{pid}/labeling-groups`）：GET 列表、POST 建立、PATCH 修改名稱／說明／成員、DELETE 刪除。
- 專案範圍唯讀 API `GET /api/projects/{pid}/labeling-groups`（需 Labeling 權限）：B-02 之後分派標註工作時用來列出「我所在的群組」與群組成員。
- 連動：把帳號移出專案時，一併移出該專案的群組；刪除帳號時移出所有群組；刪除專案時刪除它的群組（seed 重設亦同）。
- 稽核類別：**project**。理由：8 類固定；標註群組是專案的組織設定（契約把它列在「網頁式帳號與專案管理」），本身不授予任何權限
  （權限仍由角色與 5 項權限決定），所以不歸 role／permission；也不是資料（dataset）。動作 `labeling_group.create|update|delete`，
  對象 `project:{pid}/labeling_group:{gid}`，detail 記名稱與成員帳號（修改時記 from／to）。
- 網頁：帳號管理下新增「標註群組」分頁：選專案 → 群組列表（名稱、說明、成員）→ 新增／編輯（成員只能從專案成員勾選）／刪除（確認對話框）。

**測試**：API 單元測試（CRUD、409 非成員、409 重名、404、403 非 Admin、422 空名稱、稽核筆數與內容、連動移除）；Vitest 頁面；Playwright。

## 3. 稽核表的資料庫權限（TC-SS-07）

**現況**：平台 API 以 `platform`（PostgreSQL 超級使用者、所有表的擁有者）連線，可以 UPDATE／DELETE `audit_log`。

**設計**
- 兩個角色：
  - `platform`（不變）：資料庫超級使用者與資料表擁有者。只給一次性的 db-init、備份／還原、Keycloak、HAPI 等使用，不給平台程式。
  - `platform_app`（新）：平台 API、FHIR worker、bootstrap-admin、seed 使用。一般表 SELECT／INSERT／UPDATE／DELETE，序列 USAGE／SELECT；
    `audit_log` 只有 SELECT、INSERT（加上 id 序列的 USAGE／SELECT）。沒有 CREATE、TRUNCATE，不是任何角色的成員。
- 誰建表：新模組 `python -m app.db_init`，以擁有者連線（`DATABASE_OWNER_URL`）：建立或更新 `platform_app`（密碼取自 `APP_DB_PASSWORD`）、
  `Base.metadata.create_all`、有 pgvector 時建立向量表、授權、對未來的表設定預設權限（`ALTER DEFAULT PRIVILEGES FOR ROLE platform`），
  最後撤銷 `audit_log` 的 UPDATE／DELETE／TRUNCATE 並自我檢查。可重複執行，每次部署都跑，所以新程式加的表由它建立並自動授權。
- 平台 API 啟動時仍呼叫 `create_all`（表已存在時不做事；SQLite 測試照舊）。表不存在且沒有建表權限時，啟動失敗並說明要先跑 db-init。
  啟動時若發現自己可以修改 `audit_log`（例如還在用 `platform` 連線），寫一筆警告 log。
- pgvector：`PgVectorStore` 在表已存在時不再執行 DDL（`CREATE EXTENSION` 需要超級使用者），由 db-init 建立。
- compose：新服務 `db-init`（平台 API 映像，一次性），`api` 與 `fhir-worker` 等它完成；`api`、`fhir-worker` 的 `DATABASE_URL` 改用 `platform_app`。
  不放在 `init.sql`：它只在空資料卷時執行，既有環境不會套用。
- Kubernetes：`db-init` 工作改成 initContainer（psql 建各資料庫）＋ 主容器（平台 API 映像跑 `app.db_init`）；Secret 新增 `POSTGRES_APP_PASSWORD`；
  `api`、`fhir-worker`、`bootstrap-admin`、kind `seed` 的 `DATABASE_URL` 改用 `platform_app`。`create-secrets.sh` 對已存在的 Secret 只補上缺少的鍵。
- 備份／還原：`pg_dumpall --roles-only` 已含 `platform_app`；`pg_dump` 含授權與預設權限。`restore.sh` 在 `pg_restore` 後再跑一次 db-init，
  讓升級前的備份還原後也有正確權限。

**升級既有環境**
- compose：`docker compose up -d --build`（db-init 建立角色與授權，api 以新帳號重啟）。
- Kubernetes：`./create-secrets.sh`（補上 `POSTGRES_APP_PASSWORD`）→ `./deploy.sh production`（或 kind）。新 api Pod 在 db-init 完成前連不上（角色尚未建立），
  會自動重啟，約 1–2 分鐘的停機。

**測試**：`platform/api/tests/test_db_roles_pg.py`（拋棄式 PostgreSQL；`TEST_POSTGRES_URL`）：以 `platform_app` 連線，UPDATE／DELETE／TRUNCATE `audit_log` 失敗，
INSERT／SELECT 成功；其他表可讀寫；整個 API 以 `platform_app` 啟動後可建專案、寫稽核；新增的表自動有權限；db-init 可重複執行。
驗收 `platform/acceptance/test_tc_ss.py`：TC-SS-07 以平台 API 的資料庫帳號（`DATABASE_URL`）在資料庫內嘗試 UPDATE／DELETE 失敗、INSERT／SELECT 成功，
並確認沒有修改或刪除稽核的 API。部署設定的檢查放在 `platform/compliance/tests/test_k8s_manifests.py`。

## 6. 工作清單的「訊息」欄

- `sync_job` 遇到不合法的狀態轉換（例如後端短暫回報 queued，資料庫已是 running）時只寫 log，不寫進 `job.message`。
- `job_out` 不回傳舊資料中這類內部訊息（以「忽略後端回報的狀態」開頭）。
- 測試：排程單元測試。
