# 整個平台部署到 Kubernetes（k8s-deploy）Implementation Plan

> **For agentic workers:** 每個 Task 一個 commit；部署前先看 `free -m`，記憶體不夠就分批部署，不讓主機進入 swap。

**Goal:** 甲方環境整個平台跑在 Kubernetes 內（目前只有訓練與推論 Job 在叢集內，平台本身是 Docker Compose）。
以 Kustomize 提供 `base` 與兩個 overlay（`kind` 開發、`production` 範本），平台 API 以叢集內 ServiceAccount 送工作、
不用 kubeconfig；在本機 kind 叢集 `ai-platform` 部署並以經 Gateway 驗收證明可用；部署演練（TC-D02-01）可走 Kubernetes 路徑；
時間允許再做離線安裝包與離線安裝演練。

**Architecture:**

- **Kustomize（kubectl 內建）**，不引入 Helm：`platform/deploy/k8s/base`、`overlays/kind`、`overlays/production`。
  命名空間固定為 `ai-platform`（平台 API 的 Job 回連位址、ClusterRoleBinding 都依賴它）。
- **映像集中在一個檔**：`components/images/kustomization.yaml`（Kustomize Component 的 `images:`）。所有 manifest 只寫邏輯名稱
  （`ai-platform/postgres` 等），版本、digest 只出現在這一檔；`build-and-load.sh` 與離線安裝包也從這一檔讀清單。
  另一個工作者同時在改 compose 的映像版本，合併時只要改這一檔；有一個測試比對它與 compose 檔的上游映像是否一致。
- **設定由 compose 的原始檔產生**（`render-config.py`）：Keycloak realm、APISIX `config.yaml`／`apisix.yaml`、Orthanc 兩份設定、
  OHIF `app-config.js`、PostgreSQL 初始化 SQL。產生時把密碼換成環境變數佔位（Keycloak `${VAR}`、Orthanc `${VAR}`、
  APISIX `${{VAR}}`／`os.getenv`），服務名稱與 DNS 換成叢集的寫法；`--check` 模式由測試執行，compose 原始檔改了而沒重產就失敗。
  ConfigMap 不含任何密碼；密碼全部在 Secret。
- **Secret 不進版控**：`create-secrets.sh` 產生隨機密碼（或 kind 用開發值 `--dev`），以 `kubectl create secret` 建立。
  production overlay 只引用 Secret 名稱。
- **有狀態服務用 StatefulSet＋PVC**：PostgreSQL（pgvector）、Orthanc ×2、MinIO、ClamAV 病毒碼、MLflow、Mailpit 不需要。
  平台 API 的 `/data/objects`（LLM 模型目錄）也用 PVC（單一副本、Recreate）。
- **平台 API**：ServiceAccount `platform-api`；Role（`platform-jobs` 內 Job 建立／讀取／刪除、Pod 讀取）、ClusterRole（Node 讀取、
  Kueue ClusterQueue `gpu-shared` 讀取與修改）。kind overlay 另加 `nodes/status` patch（假 GPU 的份數；甲方由 NVIDIA device plugin 管，
  production 不給）。`JOB_BACKEND=kubernetes`，沒有 KUBECONFIG，`from_env` 走 in-cluster config。
- **放置**：所有平台 Pod `nodeSelector: platform/pool=cpu-web`，不上 GPU 節點。
- **NetworkPolicy**：命名空間預設拒絕所有進入流量；只有 Gateway（APISIX）、Keycloak 接受命名空間外的連線；
  API 只接受 Gateway、平台後端 Pod 與 `platform-jobs`（Job 回連工作 I/O）；Orthanc、HAPI、MinIO、推論、PostgreSQL 等只接受指定的用戶端。
- **對外**：NodePort 只有 Gateway（9080、9081）與 Keycloak；kind overlay 另有模擬 PACS 與 Mailpit（測試用）。
  既有 kind 叢集建立後不能再加 extraPortMappings，所以 `kind/expose.sh` 啟動一個轉送容器（只綁 127.0.0.1），把主機連接埠轉到 NodePort，
  流量仍經 kube-proxy 與 NetworkPolicy。主機連接埠：Keycloak 38180、Gateway 38980、OHIF 38981、PACS 38943、Mailpit 38925。
- **issuer**：與 compose 相同，`KC_HOSTNAME` 是瀏覽器用的固定網址，token 的 issuer＝`KC_HOSTNAME/realms/ai-platform`；
  API 的 `OIDC_ISSUER` 由同一個值組成（`platform-urls` ConfigMap），JWKS 與管理 API 走叢集內的 `keycloak:8080`。
- **一次性工作是 Job**：`db-init`（建資料庫，可重複）、`minio-init`、`seed`、`wiki-setup`。seed 與 API 用同一組環境與 ServiceAccount
  （重設種子會取消叢集中的工作）。
- **記憶體**：JVM（Keycloak、HAPI）以 `-XX:MaxRAMPercentage`／`-Xmx` 限制；Go（MinIO、Mailpit）設 `GOMEMLIMIT`；ClamAV 關閉並行重載。

## Global Constraints

- 只在 worktree `k8s-deploy` 工作；不改其他 worktree、`master`、`integration/wp5-8`；不 push。
- 不刪除或重建 kind 叢集；不改既有 Kueue 佇列、節點標籤、監控堆疊；compose 專案 `ai-full` 不動。
- 既有 16 個 kind 測試最後仍要通過。
- 不改 `docs/TODO.md`、路線圖、根目錄 README。文件用繁體中文。
- 結束時把平台工作負載縮到 0（保留 manifest、PVC、命名空間）。

## File Structure

```
platform/deploy/k8s/
  README.md                         使用說明（部署、測試、縮放、密碼）
  render-config.py                  由 compose 原始檔產生 base/config/*（--check 檢查是否同步）
  create-secrets.sh                 建立 Secret（--dev 用開發值；否則隨機產生）
  build-and-load.sh                 建平台映像、拉上游映像、kind load
  deploy.sh                         apply overlay、等就緒、跑一次性 Job
  scale.sh                          全部縮到 0／恢復
  components/images/kustomization.yaml   唯一的映像清單
  base/                             共同的 manifest（kustomization.yaml、各服務、RBAC、NetworkPolicy、Job）
  base/config/                      render-config.py 產生的設定檔
  overlays/kind/                    開發值、假服務、Mailpit、模擬 PACS、NodePort
  overlays/production/              範本：無假服務與模擬 PACS，網域與 TLS 佔位
  kind/expose.sh                    主機連接埠轉送容器
  offline/                          離線安裝包（bundle.sh、install.sh）
platform/acceptance/platform_exec.py   在 compose 或 Kubernetes 內執行指令的共用函式
platform/acceptance/test_k8s_deploy.py  TC-SS-05（叢集內版本）與部署檢查
platform/compliance/tests/test_k8s_manifests.py   manifest 靜態檢查
platform/compliance/compliance/discover.py         認得 Kustomize 的 images
platform/compliance/scripts/deploy-drill.sh        加 Kubernetes 路徑
docs/delivery/部署說明.md                          加 Kubernetes 步驟
```

## Tasks

1. 本計畫。
2. 設定產生器、映像清單、base 與兩個 overlay、Secret 腳本；manifest 靜態測試（`kubectl kustomize` 兩個 overlay、ConfigMap 無密碼、
   所有 Pod 有 nodeSelector、資源限制、探針、每個 Service 都有 NetworkPolicy、映像與 compose 一致、render `--check`）。
3. `build-and-load.sh`；compliance 的映像探索認得 Kustomize `images:`。
4. 一次性 Job 與 `deploy.sh`、`scale.sh`、`kind/expose.sh`。
5. 在 kind 部署、跑 seed，修到所有服務就緒。
6. 驗收的 Kubernetes 路徑（`platform_exec.py`）與 `test_k8s_deploy.py`；經 Gateway 驗收全套跑在叢集內的 Gateway。
7. 部署說明與部署演練（Kubernetes 路徑，從空命名空間開始）。
8. 時間允許：離線安裝包與離線安裝演練。

## 只能在甲方驗證

- 甲方叢集的 StorageClass、Ingress／LoadBalancer、TLS 憑證、正式網域；Keycloak 在 TLS 反向代理後的設定（`KC_PROXY_HEADERS`）。
- 甲方 CNI 對 NetworkPolicy 的實際執行（kind 用 kindnet 內建的 network policy）。
- 真實 GPU 節點（NVIDIA device plugin）下的 RBAC：production 不給 `nodes/status`，共享份數改由 device plugin 設定。
- 真實 PACS（C-FIND／C-MOVE 對外的 DICOM 連接埠與 AE 設定）、真實 SMTP、真實 LLM 與自動標註服務。
- 實際資源用量與副本數；離線安裝在甲方內網（registry 或逐節點載入）的實際做法。

過程中發現並修正：

- Keycloak 在 1 GiB 上限、預設堆積比例下首次啟動（建置 Quarkus 映像）被 OOMKilled → 上限 1280 MiB、`MaxRAMPercentage=40`。
- kind load 在 Docker 以 containerd 存映像時失敗（`--all-platforms` 找不到其他平台內容）→ `build-and-load.sh` 改以 `docker save --platform` 加節點 `ctr import`；
  MinIO 以 digest 釘住，另在節點補上 `name@sha256` 名稱。
- LLM 離線預載目錄以 ConfigMap 掛成目錄會多出 `..data`，模型 hash 與白名單不符（TC-B07-01 失敗）→ 逐檔 subPath。
- APISIX 3.19 在解析 YAML 前就替換 `${{VAR}}`，正規表示式的反斜線在雙引號內變成無效跳脫，Gateway 起不來 → 改單引號（3.11 與 3.19 都可）。
- 開發機與另一組 compose 堆疊同時跑時記憶體用盡（主機曾重開），探針 1 秒逾時讓健康的服務被連環重啟 → 探針逾時 5 秒、存活探針 6 次失敗才重啟；
  部署改分批（先核心服務，再 HAPI、推論、MLflow、ClamAV），全程看 `free -m`。

裁定：

- **Kustomize，不用 Helm**：kubectl 內建，甲方不必多裝工具；差異只有 kind／production 兩個 overlay。
- **設定由 compose 原始檔產生**（`render-config.py`），不手動維護兩份；`--check` 由測試執行。密碼一律環境變數佔位、值只在 Secret。
- **映像集中在一個 Kustomize Component**；與 compose 的上游映像不一致時測試失敗。合規的映像探索認得 Kustomize `images:`，manifest 的邏輯名稱不算映像。
- **一次性工作是暫停的 CronJob 範本**，`kubectl create job --from=cronjob/…` 執行；Job 的 Pod 範本不能改，直接 apply Job 會在第二次部署失敗。
- **甲方不跑種子**：新增 `app.bootstrap_admin`，只把 realm 匯入的 admin01 登記為平台 Admin（稽核 `account`／`admin.bootstrap`）；正式 realm 的 admin01 第一次登入要改密碼。
- **kind 的主機連接埠用轉送容器**（`kind/expose.sh`），不用 port-forward：流量照樣經 NodePort、kube-proxy 與 NetworkPolicy。連接埠 38180／38980／38981／38943／38925，只綁 127.0.0.1。
- **issuer**：`KC_HOSTNAME` 是瀏覽器用的固定網址（kind `http://localhost:38180`），平台 API 的 `OIDC_ISSUER` 由同一個 ConfigMap 值組成。
- **NetworkPolicy 只管進入流量**；平台 API 接受 `platform-jobs`（Job 回連工作 I/O），其他內部服務只接受標了 `platform/backend` 的 Pod。
- **推論服務放在 cpu-web**（照「平台服務不上工作節點」）；代價是 cpu-web 節點也要放約 6 GB 的訓練映像。
- **所有服務共用一個 PostgreSQL 帳號 `platform`**（與 compose 相同）。各服務分開帳號是正式環境的強化項目，未做。

未完成：

- **離線安裝包與離線安裝演練沒有執行**。`offline/bundle.sh`、`offline/install.sh` 已寫好（語法檢查通過），但開發機磁碟只剩約 27 GB（89%），
  安裝包估計 12–15 GB（含訓練映像與 TensorFlow 套件快取），會擠壓其他工作者。演練方法：在 kind 節點容器內暫時加 iptables 規則擋掉往叢集外的流量
  （`docker exec <節點> iptables -I FORWARD -o eth0 ! -d <kind 網段> -j REJECT`，OUTPUT 同理，演練後刪除；不動主機防火牆），刪掉 cpu-web 節點上的平台映像，
  再以 `install.sh <目錄> kind` 安裝並跑部署演練的第 5–9 步。
- 網頁前端（`platform/web`）沒有容器映像，compose 也沒有；甲方要由網頁伺服器提供打包檔，或另做映像加一條 Gateway 路由。
- Grafana 13.2.3 升級（選用）沒有做：監控堆疊不在本工作範圍內改動。
- `fhir-worker` 沒有探針（沒有連接埠，程序結束就由 Deployment 重啟）。
