# WP6 HL7 FHIR 醫療資料交換平台（C-03）Implementation Plan

> **For agentic workers:** 依 superpowers:test-driven-development 逐 Task 執行；每個 Task 一個 commit。

**Goal:** 院內來源（SQL、CSV、HL7 V2、JSON、生理監視器）經平台的對應規則轉成 FHIR R4 資源，以 Transaction 整批寫入 HAPI FHIR；外部系統只能經 APISIX Gateway、以 OAuth2／OIDC 身分存取自己租戶（＝平台專案）的資料；所有交換都有 `data_exchange` 稽核；提供排程、流量告警、Resource 關聯圖、Gateway 路由管理頁與壓測腳本。

**Architecture:** `app/fhir/` 自成一包。平台 API 透過 `FhirClient` 介面操作 FHIR 伺服器：單元測試與 S0 smoke 用 `InMemoryFhir`（同樣支援租戶、條件式 upsert、Transaction 原子性、中斷注入），整合環境用 `HttpFhir` 接 HAPI FHIR（URL 式多租戶，partition 編號與名稱都是 `{project_id}`）。ETL ＝ 讀來源 → 對應規則 → 驗證 → 一個 `Bundle(type=transaction)`；任何一筆不合格或寫入中斷都整批不寫。排程由獨立的 worker 程序（同一個映像，`python -m app.fhir.worker`）輪詢資料表執行，以資料列鎖避免多份重複執行。對外 FHIR REST 只走 Gateway：`/fhir/projects/{pid}/...` → forward-auth `/authz/check`（專案權限、路由政策、寫稽核、流量計數）→ 改寫到 HAPI `/fhir/{pid}/...`，並帶 `X-Forwarded-Prefix: /fhir/projects` 讓回應裡的網址維持對外路徑。

**Tech Stack:** FastAPI、SQLAlchemy 2、`fhir.resources`（R4B 結構驗證）、HAPI FHIR JPA Server v8.12.0（R4、PostgreSQL）、APISIX 3.11（forward-auth、DNS 服務發現）、Mailpit v1.22（告警信）。

## Global Constraints

- 沿用 WP1a：錯誤訊息繁體中文；401／403／404／409／422；測試名稱帶 TC ID；稽核與業務變更同一個交易。
- 稽核類別固定 8 類；本工作包一律用 `data_exchange`。
- 租戶＝平台專案（`docs/TODO.md` 第 2 節的暫定採用值）。讀取需該專案的 Project 權限；來源、對應規則、排程、HL7 V2 與監視器寫入、Gateway 路由管理需 Admin。
- 只用合成資料（`platform/tools/synth clinical`、`vitals`）。
- `main.py` 只加 1 個 import 與 1 個 `include_router`；compose 增量放在 `compose.fhir.yaml`；APISIX 路由附加在 `apisix.yaml` 結尾。
- 機器記憶體有限：HAPI 堆積上限 768 MB；compose 堆疊只在驗收時啟動，用完即 `down -v`。

## API

前綴 `/api/projects/{pid}/fhir`（租戶＝專案）：

| 方法與路徑 | 權限 | 說明 |
|---|---|---|
| GET `/summary` | project | 各資源型別筆數 |
| GET `/resources/{type}` | project | 瀏覽 Patient／Encounter／Observation（分頁） |
| POST `/validate` | project | 驗證一筆資源，回問題清單 |
| GET／POST `/sources`，GET／DELETE `/sources/{id}` | project／Admin | 來源：`{name, kind: sql｜csv｜hl7v2｜json, config, content}` |
| GET／POST `/mappings`，GET／PUT／DELETE `/mappings/{id}` | project／Admin | 對應規則組 |
| POST `/mappings/preview` | Admin | 對應工具預覽：規則＋樣本記錄 → 資源與驗證結果，不寫入 |
| POST `/runs` | Admin | 立即執行 `{source_id, mapping_id}`；整批 Transaction |
| GET `/runs`，GET `/runs/{id}` | project | 執行紀錄：讀取筆數、寫入筆數、錯誤原因、排定與實際時間 |
| GET／POST `/schedules`，PATCH／DELETE `/schedules/{id}` | project／Admin | `{name, source_id, mapping_id, interval_minutes, enabled}` |
| POST `/hl7v2` | Admin | 單則 HL7 V2（text/plain）；不合格回 422 並記錄原因 |
| POST `/vitals` | Admin | 生理監視器讀數（單筆或多筆）→ Observation |
| GET `/graph?patient={識別碼}` | project | 節點與邊（Patient、Encounter、Observation） |
| GET `/alerts` | Admin | 流量異常告警 |

全域：

| 方法與路徑 | 權限 | 說明 |
|---|---|---|
| GET `/api/admin/gateway/routes` | Admin | Gateway 路由清單（靜態路由唯讀、受管路由可改） |
| PATCH `/api/admin/gateway/routes/{route_id}` | Admin | 改受管路由：`enabled`、`methods`、`alert_threshold_per_minute` |
| `/fhir/projects/{pid}/{FHIR 路徑}`（經 Gateway） | 讀 project／寫 Admin | forward-auth 後轉給 HAPI 租戶 `{pid}` |

## Data Flow

1. 來源 → 記錄：SQL 以唯讀查詢取列；CSV 以標頭為鍵；JSON 為物件陣列；HL7 V2 解析成扁平記錄（`patient_id`、`family`、`visit_number`…）。
2. 記錄 → 資源：規則組內每個資源模板逐欄位套用；缺必填來源欄位、代碼不在對照表、驗證不過 → 整批拒絕並在 FhirRun 記下每筆原因。
3. 資源 → Bundle：每個 entry 用條件式 `PUT {type}?identifier={system}|{value}&_tag=urn:ai-platform:tenant|{pid}`（重跑不重複），資源帶同一個租戶標籤、`fullUrl` 為固定的 `urn:uuid`；參照用同樣帶標籤的條件式參照 `Patient?identifier=…&_tag=…`。
4. 寫入：一個 Transaction；失敗或中斷則 FhirRun＝failed，FHIR 伺服器內筆數不變。成功與失敗都寫 `data_exchange` 稽核。
5. Gateway 存取：forward-auth 每次判斷都寫一筆稽核（allowed／denied），同一使用者同一專案 60 秒內超過門檻 → 建立告警並寄信（同一分鐘不重複）。

## Tasks

1. HL7 V2 解析驗證與 FHIR 資源驗證（純函式）。
2. 對應規則引擎與 4 種來源讀取器；內建規則組。
3. FhirClient 介面、InMemoryFhir（租戶、條件式 upsert、Transaction 原子性、中斷注入）、HttpFhir。
4. 資料表與 ETL 服務：執行、HL7 V2 接收、監視器接收、稽核。
5. 路由：來源、對應、執行、資源瀏覽、驗證、關聯圖。
6. 排程與 worker。
7. Gateway：`match_fhir`（只開放固定形式的 FHIR 互動）、forward-auth FHIR 分支、路由政策、存取稽核、流量告警與寄信。
8. 部署：`compose.fhir.yaml`、APISIX 路由與 DNS 服務發現、HAPI 多租戶。
9. 經 Gateway 驗收 TC-C03-01～13 與腳本（原子性、排程、壓測、監視器）。
10. 網頁：FHIR 管理頁、關聯圖、Gateway 路由管理；Playwright。

裁定：

- 租戶＝平台專案（`docs/TODO.md` 第 2 節的暫定值）。HAPI 以 URL 式多租戶，分割區編號＝專案編號，
  並開啟 `database_partition_mode_enabled`；參照不可跨租戶。對外路徑只接受數字專案編號，到不了 DEFAULT 分割區。
- HAPI 把條件式寫入的網址存在一張不分租戶的表（HFJ_RES_SEARCH_URL，partition -1）且要求唯一，
  兩個租戶有同一位病人（同一個病歷號）時第二個會寫入失敗。可以關掉這個檢查的設定
  （`PartitionSettings.conditionalCreateDuplicateIdentifiersEnabled`）沒有開放給 starter 映像的設定檔。
  因此平台寫入的資源都帶租戶標籤 `urn:ai-platform:tenant|{pid}`，條件與條件式參照也帶 `_tag`。
  **外部系統經 Gateway 自行做條件式寫入時也要帶同樣的標籤**，否則跨租戶會撞；甲方環境若自建 HAPI 設定，建議改開上述設定。
- HAPI 開啟寫入前驗證（`validation.requests_enabled`）：經 Gateway 直接寫入不合格的資源會被 FHIR 伺服器拒絕；
  因此 Transaction 的每個 entry 都要有 `fullUrl`。
- 權限：讀取（資源、關聯圖、執行紀錄、來源與規則清單）需該專案的 Project 權限；來源、對應規則、排程、立即執行、
  HL7 V2 與監視器寫入、經 Gateway 的 FHIR 寫入、Gateway 路由管理、流量告警只給 Admin。請甲方確認。
- 稽核：資料交換一律用 `data_exchange` 類；Gateway 每次 FHIR 存取（允許與拒絕）都寫一筆 `fhir.gateway.access`。
  排程由 worker 發起，稽核的使用者記 `fhir-scheduler`、來源 IP 記 worker 自己的位址。
- 流量告警：同一使用者在同一專案 60 秒內請求數超過門檻（預設每分鐘 120，可在路由管理頁改）即告警並寄信，
  同一分鐘只寄一次；以資料庫計數，平台 API 多份時一致。告警不阻擋存取。
- Gateway 管理介面（TC-C03-03）：APISIX 是 standalone（設定檔）模式，沒有 Admin API 與官方 Dashboard 可用，
  所以做成「受管路由政策」：`fhir-rest` 路由的啟用、允許方法、告警門檻存在平台資料庫，forward-auth 每次請求即時套用；
  其他路由唯讀列出。靜態路由以路徑識別，不回傳設定檔裡的路由名稱（`/api/*` 路由名稱 platform-api 與 MinIO 存取帳號同名，TC-SS-04 會判為外洩）。
- 排程錯過的時間點（worker 停機）不補跑，只跑一次並如實記錄偏差。
- 掃毒（WP8）：來源內容（CSV、HL7 V2、JSON）與 HL7 V2 單則訊息在存入或處理前掃描；生理監視器讀數是數值 API 呼叫，不掃。
  本堆疊沒有啟動 ClamAV，掃毒只由單元測試（FakeScanner、EICAR）驗證。
- SQL 來源只接受單一唯讀 SELECT；錯誤訊息不回傳驅動原文（可能含連線字串），連線字串的密碼在 API 回應中遮蔽。
- 網頁：C-03 不在契約的 8 個功能入口內，從「帳號管理」的分頁「資料交換（FHIR）」進入（Admin）。
