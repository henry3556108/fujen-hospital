# 部署說明

本文件的步驟由 `platform/compliance/scripts/deploy-drill.sh` 逐步執行驗證（TC-D02-01）。文件與腳本的步驟一一對應，改其中一個就要改另一個。
分兩部分：第一部分是 Docker Compose（開發機整合環境）；第二部分是 Kubernetes（甲方正式環境的部署方式，開發機以 kind 叢集演練）。

# 第一部分：Docker Compose（本機整合環境）

## 需要

- Linux 或 macOS，Docker（含 compose 外掛）、git、uv；記憶體建議 8 GB 以上給 Docker。
- 若在 Proxmox LXC 容器內，主機要先開啟 nesting（見 `docs/TODO.md` 第 5 節）。

## 步驟

| 步驟 | 做什麼 | 指令（在 `platform/deploy/local` 下） | 成功的樣子 |
|---|---|---|---|
| 1 | 確認工具 | `docker info`、`git --version`、`uv --version` | 三個都有輸出 |
| 2 | 從空環境開始 | `docker compose down -v --remove-orphans` | 沒有這個專案的 volume |
| 3 | 建置並啟動 | `docker compose up -d --build --wait` | 所有服務 Running 或 Healthy |
| 4 | 等 Keycloak 就緒 | `curl -sf http://localhost:8080/realms/ai-platform` | 回 200 |
| 5 | 建立測試基線 | `docker compose exec -T api /app/.venv/bin/python -m app.seed` | 印出 3 個專案、8 個帳號 |
| 6 | Admin 登入 | 以 `admin01` 經 Keycloak 取得 token（網頁登入或密碼授權） | 取得 access token |
| 7 | 經 Gateway 呼叫 API | `GET http://localhost:9080/api/admin/projects`（帶 token） | 回 200 與 3 個專案 |
| 8 | 未登入被擋 | 同上不帶 token | 回 401 |

選用的疊加檔（依需要加 `-f`）：

| 疊加檔 | 用途 |
|---|---|
| `compose.kind.yaml` | 平台 API 把工作送進本機 kind 叢集（先執行 `platform/deploy/kind/up.sh`，再 `connect-compose.sh`） |
| `compose.compliance.yaml` | 上傳掃毒（ClamAV clamd，約 1.2 GB 記憶體；第一次啟動會下載病毒碼） |
| `compose.web.yaml` | 網頁前端的正式映像，經 Gateway `http://localhost:9082`（與 API 同源）；開發時仍可用 `npm run dev` |

其他工作包加入的疊加檔（`compose.*.yaml`）各自在檔頭說明用途。

## 自動演練

```bash
cd platform/compliance
COMPOSE_PROJECT=ai-wp8 KEYCLOAK_HOST_PORT=18380 GATEWAY_HOST_PORT=19380 PACS_HTTP_PORT=18343 \
  CONFIRM_DESTROY=ai-wp8 scripts/deploy-drill.sh
```

腳本會先刪除該 compose 專案的所有資料，所以要用獨立的專案名稱，並以 `CONFIRM_DESTROY` 明確確認。每一步印一行 PASS／FAIL，最後一行是 TC-D02-01 的結果。

# 第二部分：Kubernetes

甲方環境整個平台跑在 Kubernetes 內：命名空間 `ai-platform`，平台 API 以叢集內 ServiceAccount 把訓練與推論 Job 送到 `platform-jobs`。
manifest 在 `platform/deploy/k8s`（Kustomize：`base`、`overlays/kind`、`overlays/production`），設計與每個檔案的用途見該目錄的 `README.md`。

## 需要

- `kubectl`（1.27 以上，內建 Kustomize）、Helm **v4.3.0**（安裝方式見 `platform/deploy/k8s/README.md`「Helm」）、`python3`（含 PyYAML）、`openssl`；建置映像的機器另需 Docker。
- 叢集已安裝 Kueue 與 `platform-jobs` 命名空間的佇列（`platform/deploy/kind/kueue`），節點有 `platform/pool` 標籤：
  平台服務在 `cpu-web`，工作在 `cpu-data` 與 GPU 池。
- 有預設 StorageClass（PVC：PostgreSQL 10 GiB、Orthanc 20 GiB、MinIO 50 GiB、平台 API 10 GiB、MLflow 10 GiB、ClamAV 2 GiB）。
- CNI 要執行 NetworkPolicy（不執行時平台照常運作，但內部服務不再與外部隔離，TC-SS-05 不成立）。
- 平台節點可用記憶體：整套約 4 GB 工作集，requests 合計約 5 GB。

## 開發機演練（kind 叢集 `ai-platform`）

| 步驟 | 做什麼 | 指令（在 `platform/deploy/k8s` 下） | 成功的樣子 |
|---|---|---|---|
| 1 | 確認工具與叢集 | `kubectl config current-context`、`kubectl get nodes`、`helm version` | context 是 `kind-ai-platform`，5 個節點 Ready；Helm v4.3.0 |
| 2 | 從空命名空間開始 | `kubectl delete namespace ai-platform`（連同 PVC） | 命名空間與它的 PV 都不存在 |
| 3 | 建置並匯入映像 | `./build-and-load.sh` | 每個映像印「已載入」或「已是最新」 |
| 4 | 部署 | `./deploy.sh kind` | 依序印出各服務就緒、`db-init`、`minio-init`、`seed`、`wiki-setup` 完成，最後「完成」 |
| 5 | 等 Keycloak 就緒 | `curl -sf http://localhost:38180/realms/ai-platform` | 回 200 |
| 6 | 確認測試基線 | `kubectl -n ai-platform get jobs` | `seed-…` 成功 1 |
| 7 | Admin 登入 | 以 `admin01` 經 Keycloak（`http://localhost:38180`）取得 token | 取得 access token |
| 8 | 經 Gateway 呼叫 API | `GET http://localhost:38980/api/admin/projects`（帶 token） | 回 200 與 3 個專案 |
| 9 | 未登入被擋 | 同上不帶 token | 回 401 |

網頁：瀏覽器開 `http://localhost:38982`，按「登入」經 Keycloak 登入（admin01）。自動驗證：`cd platform/web && WEB_URL=http://localhost:38982 npm run test:e2e:real`。

`deploy.sh kind` 做的事：以開發值建立 Secret（`create-secrets.sh --dev`）、以 Helm release `ai-platform` 部署 `overlays/kind`
（`helm upgrade --install`，manifest 由 Kustomize 產生）、依序等待服務就緒並執行一次性工作、
啟動主機連接埠轉送（`kind/expose.sh`：Gateway 38980、OHIF 38981、Keycloak 38180、模擬 PACS 38943、Mailpit 38925，只綁 127.0.0.1）。

自動演練：

```bash
cd platform/compliance
DRILL_TARGET=k8s CONFIRM_DESTROY=ai-platform scripts/deploy-drill.sh
```

腳本會先刪除命名空間 `ai-platform`（含 PVC 的資料），所以要以 `CONFIRM_DESTROY` 明確確認。驗收測試：

```bash
cd platform/acceptance
export K8S_NAMESPACE=ai-platform GATEWAY_URL=http://localhost:38980 KEYCLOAK_URL=http://localhost:38180 \
       PACS_URL=http://127.0.0.1:38943 MAILPIT_URL=http://127.0.0.1:38925 OHIF_URL=http://localhost:38981
uv run pytest -q
```

開發機記憶體不夠同時跑 compose 堆疊時，用 `./scale.sh down` 把平台縮到 0（保留資料），`./scale.sh up` 恢復。

版本紀錄與退回：每次 `deploy.sh` 是 release 的一個新版本；`helm history ai-platform -n ai-platform` 列出版本，
`helm rollback ai-platform <版本> -n ai-platform` 退回（只退回 manifest，不退回資料庫與 PVC）。

## 甲方正式環境

| 步驟 | 做什麼 | 指令（在 `platform/deploy/k8s` 下） | 成功的樣子 |
|---|---|---|---|
| 1 | 映像放進甲方 registry | 平台自己的映像（`platform-api`、`platform-trainer`）`docker push` 到甲方 registry，並改 `components/images/kustomization.yaml` 的 `newName`；上游映像可由節點直接拉取（甲方環境可上網） | 叢集節點拉得到每個映像 |
| 2 | 填入網域與外部服務 | 改 `overlays/production`：`platform-urls`、`api-env`（vLLM、自動標註、SMTP）、`pacs`、`ingress.yaml`、`networkpolicy-production.yaml`、`config/app-config.js` | `kubectl kustomize overlays/production \| grep -c 'CHANGE-ME\|example.invalid'` 為 0 |
| 3 | 建立密碼 | `./create-secrets.sh`（隨機產生，不進版控） | 印出「已建立 platform-secrets」 |
| 4 | 建立 TLS 憑證 | `kubectl -n ai-platform create secret tls ai-platform-tls --cert=… --key=…` | Secret 存在 |
| 5 | 部署 | `./deploy.sh production` | 各服務就緒、`db-init`、`minio-init`、`bootstrap-admin`、`wiki-setup` 完成 |
| 6 | Admin 第一次登入 | 取得 admin01 初始密碼：`kubectl -n ai-platform get secret platform-secrets -o jsonpath='{.data.KC_ADMIN01_PASSWORD}' \| base64 -d`，從網頁登入 | 要求改密碼，改完進入管理頁 |
| 7 | 經 Gateway 呼叫 API | 以 admin01 的 token `GET https://<平台網域>/api/admin/projects` | 回 200（新環境沒有專案，回空清單） |
| 7a | 網頁 | 瀏覽器開 `https://<平台網域>/`（Ingress → Gateway 9082）並登入 | 看到 8 個入口 |
| 8 | 未登入被擋 | 同上不帶 token | 回 401 |

正式環境與 kind 的差別：沒有假服務、模擬 PACS、Mailpit、種子工作；Keycloak 所有 public client 關閉密碼授權；
`admin01` 第一次登入必須改密碼；平台 API 沒有 `nodes/status` 權限（GPU 共享份數由 NVIDIA device plugin 設定）。
甲方環境的步驟 1、2、4 依甲方的 registry、網域與憑證而定，只能在甲方環境演練。

甲方環境可以上網：ClamAV 由容器內的 freshclam 直接更新病毒碼（`clamav-env` 的 `CLAMAV_NO_FRESHCLAMD=false`，production 沿用預設），不需要預載。
`platform/deploy/k8s/offline/` 的離線安裝包與離線安裝是**選用**的，只在不能上網的環境使用；開發機曾以它從安裝包匯入映像並部署
（安裝期間以 `block-egress.sh` 擋掉 kind 節點的對外連線），因甲方確認可上網而未完成整套驗收，不列入交付演練。

# 資料庫帳號與升級（TC-SS-07）

平台資料庫有兩個帳號：

| 帳號 | 用在哪裡 | 權限 |
|---|---|---|
| `platform` | PostgreSQL 管理者與資料表擁有者：一次性的 db-init、備份與還原、Keycloak、HAPI FHIR、Wiki.js | 全部 |
| `platform_app` | 平台程式：平台 API、FHIR worker、bootstrap-admin、seed | 一般資料表讀寫、序列 USAGE／SELECT；**稽核表 `audit_log` 只有 INSERT 與 SELECT**；不能建表、不能 TRUNCATE |

db-init（`python -m app.db_init`，平台 API 映像）以 `platform` 連線：建立或更新 `platform_app`（密碼取自設定）、建立所有資料表、授權、
設定預設權限（`platform` 日後建立的表與序列自動授權給 `platform_app`），最後重設稽核表權限並自我檢查。每次部署都會執行，
所以新版本加的資料表由它建立並授權；平台 API 自己沒有建表權限，表缺少時啟動失敗並提示先跑 db-init。
平台 API 啟動時若發現自己的帳號可以修改稽核表（例如設定仍指向 `platform`），會在 log 寫警告。

- compose：`db-init` 服務（`compose.yaml`），`api` 與 `fhir-worker` 等它完成才啟動；開發密碼 `platform-app-dev`。
- Kubernetes：`db-init` 工作先以 psql 建各資料庫（initContainer），再執行 `app.db_init`；密碼是 Secret 的 `POSTGRES_APP_PASSWORD`。
  換 `platform_app` 的密碼只要改 Secret 後重新部署（db-init 每次都依 Secret 設定）。
- 備份與還原：`backup.sh` 的角色備份含 `platform_app`，資料庫備份含授權；`restore.sh` 還原後再執行一次 db-init。

## 既有環境升級

**Docker Compose**（在 `platform/deploy/local`，加上原本使用的疊加檔）：

```bash
git pull
docker compose up -d --build --wait          # db-init 建立 platform_app 與授權，api、fhir-worker 改用新帳號重啟
docker compose logs db-init | tail -1        # 「db-init 完成：帳號 platform_app，…，稽核表只有 SELECT、INSERT」
docker compose exec -T postgres psql -U platform -d platform -tAc \
  "select has_table_privilege('platform_app','audit_log','UPDATE'), has_table_privilege('platform_app','audit_log','DELETE')"   # f|f
```

不需要刪除資料卷；既有資料表仍屬於 `platform`，由 db-init 授權給 `platform_app`。

**Kubernetes**（在 `platform/deploy/k8s`）：

```bash
git pull
./create-secrets.sh            # 甲方（隨機值）；kind 由 deploy.sh 執行 --dev。Secret 已存在時既有的值不動，只補上 POSTGRES_APP_PASSWORD
./deploy.sh production         # 或 kind；db-init 建立 platform_app 與授權
kubectl -n ai-platform logs job/$(kubectl -n ai-platform get jobs -o name | grep db-init | sort | tail -1 | cut -d/ -f2) -c db-init | tail -1
```

升級時 Helm 先套用新的 api Deployment（`Recreate`），新 Pod 在 db-init 完成前連不上資料庫（`platform_app` 還不存在）會自動重啟，
平台 API 約有 1–3 分鐘無法使用；請選在離峰時段升級。
回復舊版（`helm rollback`）時，舊版 api 以 `platform` 連線，仍可運作；`platform_app` 與授權留著無害。
